# Browser active-store durability contract research

**Date:** 2026-08-20  
**Scope:** browser-local storage guarantees relevant to a provider-neutral Loomark active-store contract. This note intentionally does **not** choose IndexedDB, OPFS, Web Storage, or any combined provider.

## Scope and decision summary

A production active-store contract can require **logical commit semantics, recovery checks, integrity metadata, quota/error reporting, and observable provider capability reporting**. It cannot portably require **hardware-level fsync, exact remaining quota, indefinite retention, cross-provider multi-object atomicity, or an atomic rename primitive**.

The portable platform floor is narrower than either IndexedDB or OPFS alone:

- **IndexedDB** normatively provides transactions: a transaction is an “atomic and durable set” of data access/mutation operations, abort rolls back all changes, commit writes all changes atomically or aborts, and `complete` fires only after the database changes have been successfully written. However, the `durability: "strict"` option is explicitly a **hint**: the user agent **may** treat the transaction as committed only after verifying writes reached persistent storage, while implementations are encouraged to weigh the hint against user/device impact. Source: [IndexedDB 3.0 §2.7 transaction concept and durability hints](https://w3c.github.io/IndexedDB/#transaction-concept), [§5.4 commit](https://w3c.github.io/IndexedDB/#commit-transaction), [§5.5 abort](https://w3c.github.io/IndexedDB/#abort-transaction).
- **OPFS/File System Standard** normatively exposes file handles in Window/Worker contexts and sync access handles only in `DedicatedWorker`. `FileSystemWritableFileStream` writes are not reflected in the file until close; user agents “try to ensure” no partial writes, and the close algorithm note says it is **expected** to atomically update file contents. That is weaker than a hard multi-file transaction guarantee. `FileSystemSyncAccessHandle.flush()` is the explicit operation that ensures write modifications are reflected in the file and attempts to transfer cached modifications to the underlying storage device; `close()` only closes the handle/releases the lock and is not the flush operation. Source: [File System Standard `createWritable()`](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createwritable), [writable stream close note](https://fs.spec.whatwg.org/#create-a-new-filesystemwritablefilestream), [sync access handle `flush()` and `close()`](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle-flush).
- **Storage persistence/quota** is origin/bucket policy, not write durability. The Storage Standard says local buckets begin as `best-effort`, `persist()` can switch mode to `persistent` if permission is granted, persistent storage cannot be cleared by the user agent without origin/user involvement, and `estimate()` returns implementation-defined rough/conservative estimates. Source: [Storage Standard buckets and persistence](https://storage.spec.whatwg.org/#buckets), [persistence](https://storage.spec.whatwg.org/#persistence), [usage and quota](https://storage.spec.whatwg.org/#usage-and-quota), [StorageManager Web IDL](https://storage.spec.whatwg.org/#storagemanager).

**Decision for Loomark:** specify a provider-neutral active-store as an application-level **recoverable commit log / snapshot publication contract** over any browser provider. The provider may contribute stronger primitives, but Loomark owns the invariants that must survive provider differences: generation numbers, checksums/hash validation, atomic publish abstraction, rollback/abort semantics, startup recovery, single-writer coordination, quota backpressure, and observable degradation when persistence/durability is weaker than requested.

## Source classification

- **Normative standards:** Storage Standard, IndexedDB 3.0 Editor’s Draft, File System Standard, HTML Web Storage. These define portable web-platform guarantees.
- **Implementation/vendor behavior:** Chromium quota implementation/docs, WebKit storage policy, Firefox QuotaManager/source docs. These explain current browser behavior where standards leave quota, eviction, physical backing, or policy implementation-defined.
- **Application-owned requirements:** invariants that no provider/browser guarantees portably enough for Loomark: integrity validation, crash recovery format, user-visible backup/export expectations, provider selection, and provider capability negotiation.

## Concern-by-concern findings

### Durability

IndexedDB exposes a transaction `durability` hint. `"strict"` says the user agent **may** consider a transaction committed only after verifying outstanding changes were written to a persistent storage medium; `"relaxed"` allows considering it committed after writing to the operating system; `"default"` uses bucket default behavior. The same section calls these values a hint and says implementations are encouraged to weigh them against performance, battery, and device impact. Therefore Loomark can ask for strict-like behavior but cannot treat it as a portable fsync guarantee. Source: [IndexedDB durability hint](https://w3c.github.io/IndexedDB/#transaction-durability-hint).

For OPFS sync handles, the standard makes `flush()` the explicit reflection operation: it ensures the file contents contain modifications made through `write()` and attempts to transfer cached modifications to the underlying storage device. `close()` closes the handle and releases the lock; it is not the flush operation. This still is not a portable hardware-fsync guarantee. Source: [File System Standard `flush()`](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle-flush), [`close()`](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle-close).

Storage persistence is not write durability. The Storage Standard’s persistence mode protects storage from user-agent clearing policies, while usage/quota are estimates and bucket data is stored in an implementation-defined manner. Source: [Storage Standard persistence](https://storage.spec.whatwg.org/#persistence), [storage bottle implementation-defined storage](https://storage.spec.whatwg.org/#storage-bottles).

### Commit and abort

IndexedDB is the only reviewed standard provider with a normative transactional commit/abort model. Abort must roll back changes made during the transaction, including object-store/index additions/removals; commit must atomically write all outstanding database changes, or write none and abort on error. Source: [IndexedDB transaction lifecycle](https://w3c.github.io/IndexedDB/#transaction-lifecycle), [commit a transaction](https://w3c.github.io/IndexedDB/#commit-transaction), [abort a transaction](https://w3c.github.io/IndexedDB/#abort-transaction).

OPFS stream writes are buffered until close; aborting/cancelling a stream releases the lock without publishing the stream buffer, but the File System Standard does not define a database-style multi-step transaction over files or directories. Source: [File System Standard `createWritable()` behavior](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createwritable), [writable stream close/abort algorithms](https://fs.spec.whatwg.org/#create-a-new-filesystemwritablefilestream).

### Isolation and concurrency

IndexedDB readwrite transactions with overlapping scopes cannot start simultaneously because they could modify each other’s data mid-transaction; the first created overlapping readwrite transaction gets access until it finishes. A readwrite transaction is only affected by changes made through itself, and if it completes successfully its changes can be committed without merge conflicts. Source: [IndexedDB transaction modes](https://w3c.github.io/IndexedDB/#transaction-mode), [transaction scheduling](https://w3c.github.io/IndexedDB/#transaction-scheduling).

OPFS uses per-file locks: `FileSystemWritableFileStream` takes a shared lock and prevents sync access handles; `FileSystemSyncAccessHandle` takes an exclusive lock and prevents further sync handles or writable streams until closed. Source: [File System Standard lock note](https://fs.spec.whatwg.org/#file-entry-lock), [`createWritable()` lock](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createwritable), [`createSyncAccessHandle()` lock](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createsyncaccesshandle).

Web Storage is a poor active-store substrate for concurrent authors: the HTML Standard exposes `Storage` only on Window, says `localStorage` provides shared state, and explicitly does not define interaction with other agent clusters in a multiprocess user agent; authors are encouraged to assume no locking mechanism. Source: [HTML Web Storage introduction](https://html.spec.whatwg.org/multipage/webstorage.html#introduction-16), [`Storage` Web IDL exposed on Window](https://html.spec.whatwg.org/multipage/webstorage.html#the-storage-interface).

### Atomic replacement

IndexedDB commit is atomic at the transaction/database-change level. Source: [IndexedDB commit atomic write requirement](https://w3c.github.io/IndexedDB/#transaction-lifecycle).

OPFS `createWritable()` gives only a one-file replacement shape: changes are not reflected until close, user agents try to avoid partial writes, and the close algorithm note says the content update is expected to be atomic. Directory `removeEntry({recursive:true})` is explicitly allowed to fail non-atomically, and the current File System Standard interface includes `getFileHandle`, `getDirectoryHandle`, `removeEntry`, and `resolve`, but no standard rename/move transaction primitive. Source: [File System Standard `createWritable()`](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createwritable), [close atomicity expectation](https://fs.spec.whatwg.org/#create-a-new-filesystemwritablefilestream), [`removeEntry()` non-atomic recursive removal](https://fs.spec.whatwg.org/#api-filesystemdirectoryhandle-removeentry), [`FileSystemDirectoryHandle` Web IDL](https://fs.spec.whatwg.org/#api-filesystemdirectoryhandle).

### Worker access and transfer

`navigator.storage` is exposed on both `Navigator` and `WorkerNavigator`; `StorageManager.estimate()` and `persisted()` are exposed to Window and Worker, while `persist()` is Window-only in the Storage Standard. Source: [Storage Standard NavigatorStorage mixin and StorageManager Web IDL](https://storage.spec.whatwg.org/#storagemanager).

IndexedDB is exposed in Window and Worker contexts in the IndexedDB 3.0 IDL, and the introduction discusses multiple clients including pages and workers using one database simultaneously. Source: [IndexedDB introduction multiple clients](https://w3c.github.io/IndexedDB/#introduction), [IndexedDB Web IDL index](https://w3c.github.io/IndexedDB/#idl-index).

OPFS handles are serializable and exposed in Window and Worker contexts; `FileSystemSyncAccessHandle` is exposed only in `DedicatedWorker`. Source: [File System Standard handle serialization/exposure](https://fs.spec.whatwg.org/#api-filesystemhandle), [`FileSystemFileHandle` and sync handle exposure](https://fs.spec.whatwg.org/#api-filesystemfilehandle), [`FileSystemSyncAccessHandle` Web IDL](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle).

Web Storage is Window-only; that makes it unsuitable for a worker-owned active store without proxying through a Window. Source: [HTML `Storage` Web IDL](https://html.spec.whatwg.org/multipage/webstorage.html#the-storage-interface).

### Quota, persistence, and eviction

The Storage Standard defines storage usage as an implementation-defined rough estimate, quota as an implementation-defined conservative estimate, and says quota must not be a function of currently available device space. `estimate()` returns those values; it can reject on internal errors. Source: [Storage Standard usage and quota](https://storage.spec.whatwg.org/#usage-and-quota), [`estimate()` algorithm](https://storage.spec.whatwg.org/#dom-storagemanager-estimate).

By default, local storage buckets are `best-effort`. Persistence requires the `persistent-storage` permission and, when granted, protects storage from user-agent clearing policies: the user agent cannot clear persistent storage without origin or user involvement. Source: [Storage Standard bucket mode](https://storage.spec.whatwg.org/#buckets), [persistence](https://storage.spec.whatwg.org/#persistence), [`persist()` algorithm](https://storage.spec.whatwg.org/#dom-storagemanager-persist).

Chromium’s quota subsystem enforces browser-level and origin-level disk limits for quota-integrated web storage APIs, stores last-accessed time in a quota SQLite database, and uses that for LRU eviction under storage pressure. Source: [Chromium quota README](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/storage/browser/quota/README.md).

WebKit’s current policy covers storage APIs including localStorage, Cache API, IndexedDB, Service Worker, and File System. Safari 17 browser-app origin quota is up to 60% of disk and overall quota up to 80%; storage operation failure throws `QuotaExceededError`; eviction normally deletes an origin as a whole using least-recently-used order, and default best-effort origins can be evicted while persistent-mode origins may be excluded. WebKit also states `estimate().quota` is only an upper limit and may vary for privacy. Source: [WebKit Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/).

Firefox’s implementation selects inactive origins for eviction, skips `LockedPersisted()` origins, sorts inactive origins with `OriginInfoAccessTimeComparator()`, locks selected origins for eviction, deletes origin directories, and later notifies storage pressure if temporary usage remains high. Source: [Firefox QuotaManager source: collect inactive origins](https://searchfox.org/mozilla-central/source/dom/quota/ActorsParent.cpp#5498-5523), [LRU collection](https://searchfox.org/mozilla-central/source/dom/quota/ActorsParent.cpp#5801-5859), [deleting origin directories and storage pressure](https://searchfox.org/mozilla-central/source/dom/quota/ActorsParent.cpp#21248-21445).

Explicit user/browser data clearing is separate from eviction. Firefox documents data sanitization as a browser UX feature rather than a web-platform standard; Firefox can clear site data manually or on shutdown, and its ClearDataService centralizes deletion of browser state. Source: [Firefox Source Docs: Data Sanitization](https://firefox-source-docs.mozilla.org/toolkit/components/antitracking/anti-tracking/data-sanitization/index.html).

### Corruption and crash recovery

None of the reviewed standards gives Loomark an end-to-end guarantee that a logical active-store state can be recovered after arbitrary browser crash, OS crash, power loss, device failure, profile corruption, user clearing, or cross-provider partial publication. IndexedDB gives transaction-level atomicity and commit/abort; OPFS gives sync `flush()` and one-file stream close atomicity expectation; Storage persistence reduces automatic eviction risk but does not validate data integrity or reconstruct logical state. Sources: [IndexedDB commit/abort](https://w3c.github.io/IndexedDB/#commit-transaction), [File System Standard flush/close](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle-flush), [Storage Standard persistence](https://storage.spec.whatwg.org/#persistence).

Therefore Loomark must own: versioned records, checksums/content hashes, generation/epoch ordering, idempotent replay or snapshot selection, detection of torn/incomplete provider writes, recovery from missing provider data, and user-visible backup/export/sync strategy for irreplaceable state.

### Observability

The portable observability surface is limited but enough for capability reporting:

- Storage API: `persisted()`, Window-only `persist()`, and `estimate()` return persistence mode and rough usage/quota. Source: [StorageManager Web IDL](https://storage.spec.whatwg.org/#storagemanager).
- IndexedDB: transaction `complete`, `abort`, `error`, `transaction.error`, `transaction.durability`, and errors such as `QuotaExceededError` can be observed. Source: [IndexedDB transaction events](https://w3c.github.io/IndexedDB/#transaction-lifecycle), [`IDBTransaction` Web IDL](https://w3c.github.io/IndexedDB/#idbtransaction).
- OPFS: write/flush/close methods throw or reject according to their algorithms; `write()` returns bytes written for sync handles and can expose partial writes; directory iteration order and concurrent inclusion are explicitly not guaranteed. Source: [File System Standard sync `write()`](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle-write), [`flush()`](https://fs.spec.whatwg.org/#api-filesystemsyncaccesshandle-flush), [directory iteration caveat](https://fs.spec.whatwg.org/#api-filesystemdirectoryhandle-asynciterable).

## Recommended provider-neutral active-store contract

A production Loomark active-store contract can safely require:

1. **Logical committed generation:** after `commit` resolves, subsequent opens must either observe that committed generation or a later committed generation, never an unvalidated partial generation. Provider-native transaction or file-close semantics may implement this, but Loomark verifies it with generation metadata.
2. **Abort/rollback behavior:** a failed or aborted write must not publish a new generation. On startup, incomplete generations are ignored or repaired.
3. **Integrity validation:** every committed generation carries format version, length, content hash/checksum, and monotonic sequence/epoch. Invalid generations are rejected with an observable recovery result.
4. **Single-writer coordination:** the active store has one writer authority per logical store. Provider locks/transactions are used when available; Loomark supplies a lease/coordination layer when the provider cannot guarantee it portably.
5. **Capability reporting:** provider reports transaction support, file-flush support, atomic-one-file publish support, worker availability, persistence status, approximate usage/quota, and durability hint support. These are observations, not universal guarantees.
6. **Quota and persistence discipline:** the application requests/checks persistence where appropriate, treats `estimate()` as approximate, handles quota failures at write time, and exposes user-facing export/sync/compaction for irreplaceable data.
7. **Recovery before use:** opening an active store performs recovery/validation before returning writable state; failures are explicit and distinguish missing/evicted storage, quota error, corruption, unsupported provider, and user-cleared data.

The contract should not require:

- exact byte quota or guaranteed remaining capacity;
- immunity from user clearing, privacy policy deletion, profile deletion, private-browsing cleanup, or device failure;
- hardware fsync semantics after every browser-level commit;
- standard atomic rename/move over OPFS;
- multi-file atomicity unless a selected provider advertises and verifies it;
- Web Storage as a worker-safe or concurrency-safe active-store provider.

## Unresolved provider-selection boundary

This note deliberately stops before provider selection. The next decision must choose how Loomark maps its logical contract onto concrete providers: IndexedDB transactions, OPFS single-file/sync-handle formats, a hybrid metadata/blob layout, or a fallback tier. That decision should be based on workload shape, data size, worker topology, migration cost, browser support target, and measured performance—not on assuming browser storage provides stronger portable durability than the primary sources above actually specify.
