# Progressive editable-restore UX (#1309)

## Scope and decision frame

This note answers the UX question in [issue #1309](https://github.com/dowdiness/canopy/issues/1309): what should Loomark show when canonical Markdown is readable before an editable causal state is available, an accelerator is rejected, or history replay is slow/fails? It does **not** choose a storage provider, retained representation, or implementation interface.

The Loomark constraint is stronger than ordinary offline editing: the operation graph is Causal Authority, current text is a materialized state, and derived views/caches are not authoritative ([`local-first-document-ownership.md`](../design/local-first-document-ownership.md#four-authorities-kept-distinct)). Therefore, readable text may be presented before edit admission, but typing must not silently create causal history from a state that has not been accepted. That is an inference from the internal authority boundary, not a product fact.

Evidence labels used below:

- **Observed** — behavior or product limitation stated in first-party product documentation.
- **Guidance** — normative guidance from a standards/design owner.
- **Inference** — application of that evidence to Loomark’s authority boundary.

## Primary-source product and research evidence

| Family | Observed behavior / published position | Loomark transfer and authority verdict |
| --- | --- | --- |
| **Google Docs offline: prepared-readiness gate** | Google says Docs/Sheets/Slides can be created, viewed, and edited offline when offline access is enabled and a file is available; if a document is “not ready to edit offline,” an explanation appears. [S1] | **Positive UX transfer (inference):** show useful canonical content while edit readiness is separately resolved, and explain why edit is unavailable. Do not infer that Google’s offline representation is Loomark’s causal state. |
| **VS Code: local restart recovery / Hot Exit** | VS Code backs up unsaved changes so they can be restored after an unexpected close; Hot Exit remembers unsaved files and restores windows on the next launch. The product exposes a dirty indicator and configurable restore behavior. [S2] | **Positive UX transfer (inference):** a recovery path can keep the familiar document surface and restore without making the user start over. **Authority failure if copied literally:** a text backup is not Loomark’s accepted causal history; it cannot be presented as the same editable branch without validation. |
| **Figma: offline queue with explicit sync review** | Figma keeps the current/loaded pages available offline, stores offline changes locally, shows an offline/unsaved indicator, and later presents an “Open to sync”/“Later” review flow. It offers a `.fig` snapshot as a last-resort copy, warns that discard is irreversible, and reports conflicts with a Review action. It says autosave can survive closing the tab/browser or shutting down, subject to browser storage limits. [S3] | **Strongest UX transfer (inference):** persistent, user-visible recovery state; defer/continue-reading action; explicit retry/sync review; copy/export escape hatch; distinguish discard from failure. **Authority limit:** Figma’s queued edits are valid in its model; Loomark must not queue edits against unaccepted causal state unless a separate, explicitly named object is chosen later. |
| **Automerge: local-first causal state** | Automerge describes local copies as independently editable offline, saved locally, then synchronized; it keeps change history and supports old versions, comparison, branches, and merge choices. It describes immutable snapshots and automatic merging. [S4] | **Conditional design evidence (inference):** provisional branches and queued edits are coherent when the local causal document is itself authoritative. Loomark’s canonical text can be displayed optimistically, but an unvalidated accelerator is not equivalent to Automerge’s accepted local state. |
| **Original local-first research** | Kleppmann et al. define local-first software around local ownership, offline operation, collaboration, and user control. They recommend “no spinners”/work at the user’s fingertips, while noting that optimistic UI can appear complete and later fail; they distinguish local primary data from server copies. [S5] | **Material challenge to blank/blocking UX (inference):** do not hide already-readable text behind replay. **Material warning against unlabelled optimistic editing (inference):** an action that later fails must not have been represented as committed Loomark history. |

**Platform guidance:** Apple’s Human Interface Guidelines frame progress indicators as a way to show that an app is not stalled while loading content or performing a lengthy operation; Material Design distinguishes determinate/indeterminate indicators and documents phased loading. Neither source supplies a universal millisecond threshold. This supports a product-calibrated disclosure budget, not a fixed number. **Guidance plus inference.** [S11][S12]

### What is materially better than the current candidate?

**Yes: a composite progressive mode is materially better.** Keep canonical text readable immediately, but expose a stable, non-modal recovery state once work exceeds a short product-calibrated budget; retain that state through accelerator rejection and replay; and provide explicit Retry, Continue reading, and Copy/Export actions on delay or failure. Coalesce a fast reject-and-replay into one final “Editing ready” status rather than surfacing implementation jargon. This combines Google’s separate edit-readiness explanation, Figma’s persistent review/retry/copy semantics, VS Code’s same-surface restart recovery, and local-first “no spinners” guidance. This paragraph is an **inference**, not an observed implementation of any one product. [S1][S2][S3][S5]

## Alternative designs and authority analysis

| Alternative | Why it succeeds or fails | Rank |
| --- | --- | --- |
| **Progressive canonical read-only, then same-surface edit activation** | Succeeds: readable value is available immediately; editability is honest; a bounded status explains a delay; the eventual editor need not change document identity. The recommendation to preserve the same content surface, scroll, focus, and selection is an inference supported by W3C’s logical-focus-order requirement and HTML’s native read-only control semantics. [S1][S2][S3][S8][S9] | **1 — recommend** |
| **Read-only plus persistent recovery tray** | Succeeds: makes “accelerator rejected,” “rebuilding,” “retry,” and “copy” discoverable without blocking reading. Figma’s review banner and last-resort export are direct precedents; W3C says status messages should be programmatically exposed without taking focus. [S3][S6][S7] | **1A — part of recommendation** |
| **Skeleton/blank until editable** | Fails when canonical text already exists: it removes useful value, turns a recoverable delay into an opaque wait, and conflicts with local-first “no spinners.” A phased loading indicator can be appropriate when no content is available, but not as a reason to conceal known text. [S5][S11] | **Rejected for this state** |
| **Queued typing against canonical text** | Succeeds for products whose local document state is already accepted (Figma/Automerge). Fails Loomark’s causal authority constraint if queued edits can later be reinterpreted, dropped, or rebased without an explicit user-visible boundary. [S3][S4][S5] | **Rejected by current authority boundary** |
| **Optimistic editable provisional branch** | Could preserve responsiveness and later offer merge/review, and Automerge explicitly discusses branches. But it changes the user’s apparent object: a provisional branch is not the canonical document until accepted. Without a distinct label and explicit disposition, it misrepresents authority. The product may revisit it only as a separate recovery mode; this note does not choose that mode. [S4][S5] | **Deferred / conditional** |
| **Automatic accelerator discard and silent fallback** | Safe for canonical text if the accelerator is only a cache, but silence hides a meaningful change in recovery state. Figma’s unsynced/conflict banners and Google’s “not ready to edit” explanation support disclosure when user-visible delay or capability changes. [S1][S3] | **Rejected as silent behavior; retain automatic fallback** |
| **Always block until editable** | Fails the available-text case and local-first responsiveness goal. It is only defensible when no trustworthy canonical text exists. [S1][S5] | **Rejected for this state** |
| **Immediate “edit as new document” fallback** | Could preserve agency after causal recovery failure, but it necessarily creates a new identity/history boundary. It must never be presented as continuation of the failed document. Whether Loomark should offer it is a product decision, not a research conclusion. [S3][S5] | **Decision question, not selected** |

## Scenario matrix

| Scenario | Visible state and input policy | Recovery/failure semantics | Assistive technology, focus, selection | Verdict |
| --- | --- | --- | --- | --- |
| **Fast success** | Render canonical text immediately in the eventual document surface, read-only. Validate the accelerator in the background; activate editing without a blank/skeleton transition when accepted. No typing before activation. | Coalesce the fast path to “Editing ready”; do not expose accelerator internals when no user-visible delay occurred. **Inference** from the products’ readiness/status separation. [S1][S2] | Keep the same landmark/control where possible. Do not steal focus merely because editability changed; expose the readiness change as a status message. W3C says status need not take focus. [S7][S9] | Best default. |
| **Slow validation** | Canonical text remains readable and selectable; surface a persistent, non-modal “Preparing editing” status after a short, product-calibrated delay. Do not replace text with a blank loader. | Offer Continue reading and Retry; do not claim “saved” or “editable” until causal admission succeeds. The exact time budget is an open product measurement, not a source fact. [S5][S11] | Use a programmatically determinable status; avoid repeated assertive announcements. Keep reading order, scroll, and focus stable. [S7][S8][S9] | Preferred delayed path. |
| **Accelerator rejected; fallback succeeds** | Keep the same canonical text. Automatic rejection is invisible as an implementation detail only while fallback completes within the short budget; otherwise update the persistent status to “Rebuilding editing from document history.” | Treat rejection as cache failure, not document loss. Do not discard canonical text. On success, announce edit readiness; if delay crosses the budget, expose Retry/details. [S1][S3] | Announce the capability transition once through status; do not move focus to a toast or re-create the text control. [S7][S8][S9] | Better than silent discard. |
| **Slow fallback** | Continue showing canonical text; status says rebuilding and, if measurable, exposes phase/progress. Keep read-only input disabled from mutation, not removed from the tree. | Continue reading must not cancel recovery. Retry may restart validation; the UI must distinguish still working from failed. Material guidance supports indicators for ongoing/lengthy work and phased loading, not hiding known content. [S11] | `role=status`/equivalent programmatic status is appropriate for waiting/progress; avoid a modal that interrupts reading. [S7][S8] | Preferred. |
| **Fallback failure; readable text remains** | Preserve the full readable canonical text as the primary surface. Enter an explicit recovery mode with a durable error summary and controls: Retry, Copy Markdown, Download/Export, and (if product later approves) create a clearly new document. | Never imply that text is editable/causally continued. Explain “editing recovery failed; readable content is preserved,” distinguish retryable failure from invalid/corrupt input, and make discard irreversible only after explicit confirmation. Figma documents both export and irreversible discard semantics. [S3] | Keep the error in the page flow and expose it as a status/error; use an alert only for important time-sensitive failure, never as a focus-stealing convenience. Do not auto-remove the only explanation. [S7][S8] | Required trust boundary. |
| **Restart during recovery** | On reopen, re-present canonical text read-only and the durable “recovery pending/failed” state; rerun recovery idempotently or offer Retry. Never infer success from a stale loading flag. | If the app had not accepted edits, there is no queued user text to silently lose. If a future provisional mode is approved, its branch/queue must have its own explicit durability and restart contract; this note does not select a representation. VS Code and Figma show that restart-surviving recovery is a recognizable product pattern, but their state models differ. [S2][S3] | Restore focus only when a prior target is still semantically valid; otherwise land at the document heading/status in logical order. Preserve text position rather than forcing a modal. [S7][S9] | Required restart rule. |
| **Assistive-technology behavior** | Canonical text must be real readable content, not only painted skeletons. The read-only state should expose its name and read-only/busy status; the editable state should expose the corresponding change. | Statuses are part of the failure contract, not decoration: “preparing,” “editing ready,” “rebuilding,” and “editing recovery failed” must be distinguishable. | WCAG 2.2 requires status messages to be programmatically determinable without receiving focus; WAI-ARIA APG says alerts should not affect keyboard focus and should not disappear too quickly; WCAG requires logical focus order. Use polite status for progress, assertive alert only for important errors, and preserve selection/caret when the underlying text is unchanged. [S7][S8][S9][S10] | Non-optional acceptance condition. |

## Ranked recommendation

1. **Adopt progressive canonical read-only with same-surface activation and a persistent recovery/status tray.** Show the value immediately; gate only mutation; disclose delayed/rejected/failed recovery; keep Retry and Copy/Export available; preserve focus, reading order, scroll, and selection where text is unchanged. This is the only option that satisfies both “work is at hand” and “canonical text is not causal history” without inventing a new authority. **Inference from [S1]–[S5], [S7]–[S11].**
2. **Consider an explicit new-document recovery action only after a product decision.** It can maximize user agency after causal failure, but must clearly sever identity/history and must not masquerade as restoration. **Inference from [S3][S5] and the internal authority boundary.**
3. **Do not use blank/skeleton, silent discard, queued typing, or provisional editing as the default.** They either hide available value, conceal a meaningful state change, or blur causal authority. **Inference from [S3]–[S5], [S7][S8].**

## Decision questions still requiring the user

- What measured delay budget should change a quiet fast path into a persistent recovery disclosure, and should that budget vary by device/document size?
- Should “Copy/Download Markdown” always be available, or only after fallback failure?
- Is “Edit as new document” a permitted explicit recovery mode, and what wording makes the new identity/history boundary unmistakable?
- Which recovery failures are retryable, and when should Retry stop automatically to avoid repeated work?
- What selection/caret restoration guarantees are acceptable when canonical text is unchanged but the editor control changes mode?
- Which status updates should be polite versus assertive for the supported screen readers and speech-input users?
