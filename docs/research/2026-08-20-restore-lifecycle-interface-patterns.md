# Restore/readiness lifecycle interface patterns: primary-source study

- Ticket: [Research restore lifecycle interface patterns (#1321)](https://github.com/dowdiness/canopy/issues/1321)
- Map context: [Production editable-branch restore architecture (#1295)](https://github.com/dowdiness/canopy/issues/1295)
- Date: 2026-08-20
- Scope: primary-source pattern study only. This note does **not** select Loomark's final interface, retained-state representation, or storage adapter.

## Reading the current Loomark seam

The current implementation already separates readable archive material from causal admission. `decode_json_string` returns a structurally decoded archive whose history has not been admitted; admission happens later through `classify_local_archive_record`. ([archive decode](../../apps/loomark/archive/archive.mbt#L157-L216), [repository classification](../../apps/loomark/repository/repository.mbt#L58-L63))

The repository classification is a compact snapshot enum: `Missing`, `Valid(ReopenedLocalArchive)`, or `Rejected(LocalArchiveLoadFailure)`. The standalone bootstrap reads storage, classifies the loaded record, mounts a valid reopened editor, or mounts a recovery application. ([classification](../../apps/loomark/repository/repository.mbt#L109-L160), [bootstrap](../../apps/loomark/internal/rabbita/standalone_bootstrap.mbt#L131-L162)) The storage adapter already returns `Missing`, `Loaded(String)`, or typed `Failed(...)`, and writes return a typed completion correlated by request ID. ([storage implementation](../../apps/loomark/internal/archive_storage/storage.mbt#L18-L37), [generated storage interface](../../apps/loomark/internal/archive_storage/pkg.generated.mbti#L15-L37))

The generated Rabbita interface exposes `mount_standalone` but no public restore/mount lifecycle type; the generated repository interface exposes classification and `ReopenedLocalArchive`, not an application-facing readiness stream or mount capability. ([generated Rabbita interface](../../apps/loomark/internal/rabbita/pkg.generated.mbti#L31-L47), [generated repository interface](../../apps/loomark/repository/pkg.generated.mbti#L28-L91)) The private editor runtime already treats `RawRecovery` as terminal for one mount, while the focus runtime versions a logical target with a source revision and rejects stale tokens. ([recovery reducer](../../apps/loomark/internal/rabbita/recovery_state.mbt#L1-L48), [focus token codec](../../apps/loomark/internal/rabbita/focus_runtime.mbt#L36-L74))

**Inference:** the open question is not whether the repository can classify an archive. It is whether the seam from classification to Rabbita Session assembly should expose a richer lifecycle carrier that keeps canonical text readable while causal authority is pending, rejected, or being rebuilt.

## Accepted lifecycle used for comparison

The accepted product contract distinguishes canonical Markdown readability from editable causal readiness. It requires a read-only selectable/copyable surface while admission or rebuild runs, automatic fallback from a rejected accelerator to canonical full history, an explicit read-only terminal state when reconstruction fails, and no queued or provisional edits. On successful activation it requires preservation of scroll, focus, the full directed selection (anchor, focus, and direction), and exact UTF-16 bounds. ([accepted resolution](https://github.com/dowdiness/canopy/issues/1296#issuecomment-5353141513), [selection-direction correction](https://github.com/dowdiness/canopy/issues/1296#issuecomment-5353207094))

## Primary-source pattern cards

### 1. Automerge Repo `DocHandle` and `DocumentProgress`

The Automerge Repo documentation describes `DocHandle` as a live wrapper around a document: changes are persisted and synchronized, inbound changes emit a `change` event, and a handle can be waited on while it is loaded or retrieved from peers. ([DocHandles guide](https://automerge.org/docs/reference/repositories/dochandles/)) The guide's legacy state enum names `IDLE`, `AWAITING_NETWORK`, `LOADING`, `REQUESTING`, `READY`, `DELETED`, and `UNAVAILABLE`; it also records that an unavailable document can later become ready when a peer arrives. ([DocHandles state guide](https://automerge.org/docs/reference/repositories/dochandles/#dochandle-states))

The current generated documentation has split this into a read-only `DocumentProgress<T>` query with `state: "loading" | "ready" | "unavailable" | "failed"`, `peek()`, `subscribe(callback)`, and `whenReady({ signal })`; the `DocHandle` is returned only once the query is ready. ([`DocumentProgress`](https://automerge.org/automerge-repo/interfaces/_automerge_automerge-repo.DocumentProgress.html)) The first-party `DocumentQuery` source also exposes per-source `pending`/`ready`/`unavailable` states, allows an unavailable query to return to loading when a source becomes pending again, and makes `fail` terminal. ([`DocumentQuery.ts`](https://raw.githubusercontent.com/automerge/automerge-repo/main/packages/automerge-repo/src/DocumentQuery.ts)) Current `Repo.find` source says an abort signal cancels the wait, not the underlying document load; the query and its sources remain active for concurrent callers. ([`Repo.find` source](https://raw.githubusercontent.com/automerge/automerge-repo/main/packages/automerge-repo/src/Repo.ts))

A current `DocHandle` is therefore both a capability object and an event source: its documented `change` method records mutations and the repository persists/synchronizes them, while a view-pinned handle fixes heads and rejects mutations. ([`DocHandle` class](https://automerge.org/automerge-repo/classes/_automerge_automerge-repo.DocHandle.html), [current source](https://raw.githubusercontent.com/automerge/automerge-repo/main/packages/automerge-repo/src/DocHandle.ts))

**Pattern lesson (inference):** keep a readable progress snapshot/event stream separate from the mutation-capable object. Do not make cancellation of one observer imply cancellation of shared loading. A terminal `unavailable`/`failed` query state can remain observable without manufacturing a mutation capability.

### 2. VS Code working-copy, backup, and editor lifecycle

`IWorkingCopyService` publishes registration, unregistration, dirty-state, content, and save events; it also exposes current working-copy collections and dirty/modified queries. Registration enforces one working copy per resource/type, wires the events, emits initial registration/dirty signals, and returns a disposable that unregisters the working copy. ([`workingCopyService.ts`](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyService.ts))

`WorkingCopyBackupTracker` consumes those events. It schedules delayed backup work after content changes, cancels a prior operation before scheduling a replacement, passes a `CancellationToken`, checks that content is still modified before storing, discards backups when clean, and cancels/suspends pending work during shutdown. ([`workingCopyBackupTracker.ts`](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts)) Its restore path waits for the restored lifecycle phase, enumerates backups, waits for a matching editor handler, creates editors for backups without an open editor, opens them pinned/inactive with `preserveFocus: true`, resolves them, and removes handled backups from the unrestored set. ([restoreBackups source](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts)) VS Code names `Ready`, `Restored`, and `Eventually` lifecycle phases and warns that work before `Restored` can block the editor from showing. ([`lifecycle.ts`](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/lifecycle/common/lifecycle.ts))

The editor handler interface is capability-shaped: `handles` may be synchronous or asynchronous, `isOpen` identifies an existing editor, and `createEditor` may be synchronous or asynchronous. Handler registration itself is an event and returns a disposable. ([`workingCopyEditorService.ts`](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyEditorService.ts))

**Pattern lesson (inference):** readiness is assembled from independently observable working-copy state, delayed work, and a late-registered editor capability. Restart is a new registration/handler pass, not a mutation of the old editor. Focus continuity is an explicit opening option (`preserveFocus`) rather than an accidental consequence of readiness.

### 3. Elm Architecture, `Task`, `Cmd`, and `Process`

Elm's official architecture guide defines the core loop as Model, View, and Update: input becomes a message, `update` produces a new model, `view` renders it, and the loop repeats. ([Elm Architecture](https://guide.elm-lang.org/architecture/), [button example](https://guide.elm-lang.org/architecture/buttons.html))

The `Task` source defines a task as a description of an asynchronous operation that may succeed or fail. `andThen` chains tasks, `onError` recovers, and `perform` or `attempt` turns a task into a `Cmd`; `attempt` maps success and failure into a `Result` message for `update`. ([Elm `Task.elm`](https://raw.githubusercontent.com/elm/core/1.0.5/src/Task.elm)) The official effects guide describes `Cmd` and `Sub` as values sent to the runtime to interact with the outside world. ([Elm commands and subscriptions](https://guide.elm-lang.org/effects/))

Elm's `Process` module exposes `spawn`, `sleep`, and `kill`; its source explicitly says `kill` forces a process to stop and aborts an in-flight HTTP request when that request is the task being run. ([Elm `Process.elm`](https://raw.githubusercontent.com/elm/core/1.0.5/src/Process.elm))

**Pattern lesson (inference):** a reducer can make authority readiness, restart, terminal failure, and stale-result rejection explicit as messages and model states. Async work remains outside the pure reducer, and cancellation must be modeled by the effect owner (`Process.kill` or an equivalent command identity), not inferred from a snapshot alone. Focus continuity must be a message/effect contract if it matters; Elm's generic reducer does not provide it automatically.

### 4. Ports and adapters: Cockburn's original pattern

Cockburn's original 2005 article states the intent as allowing an application to work without either a UI or a database, so it can be tested in isolation, work when the database is unavailable, and link applications without user involvement. It defines a port as a purposeful conversation and an adapter as the technology-specific translator between an external event and the application's procedure/message. ([Cockburn, “Hexagonal Architecture”](https://alistair.cockburn.us/hexagonal-architecture))

The article explicitly allows multiple adapters for one port, including a GUI, test harness, batch driver, HTTP connection, in-memory database, and real database, while the application's functional specification targets the inner port conversation rather than an external technology. ([Cockburn, “Structure” and “Nature of the Solution”](https://alistair.cockburn.us/hexagonal-architecture))

**Pattern lesson (inference):** if the restore lifecycle interface is a port, browser storage, full-history reconstruction, and Rabbita effects can be adapters. The port earns depth only if it owns lifecycle ordering and failure semantics; a port that merely forwards `Loaded(String)` and `Valid(ReopenedLocalArchive)` is shallow.

### 5. Capability objects: UCAN's primary capability description

The UCAN specification describes object capabilities as combining references, encapsulated state, and proxy forwarding. It describes authority as being passed through delegation rather than an intermediary authorization server, and it names delegation, invocation, promise, and revocation as lifecycle elements. ([UCAN specification, “Object Capabilities” and “Lifecycle”](https://raw.githubusercontent.com/ucan-wg/spec/main/README.md))

The same specification requires execution-time validation of the authority used by an invocation and defines validity intervals with optional `nbf` and recommended `exp` time bounds. ([UCAN specification, “Security Considerations,” “Execution-Time,” and “Validity Interval”](https://raw.githubusercontent.com/ucan-wg/spec/main/README.md))

**Pattern lesson (inference):** a Loomark mutation capability could be represented as an unforgeable value whose possession means causal admission succeeded, while read access remains available without it. But UCAN is a cryptographic delegation scheme, not a ready-made document restore interface; importing its token/delegation machinery would violate the current non-goal unless a real authority-transfer problem appears.

## Scenario comparison

| Scenario | Primary-source evidence | Consequence for any Loomark interface (inference) |
|---|---|---|
| Cancellation | Automerge aborts a caller's `whenReady` wait without stopping shared loading ([A2](https://automerge.org/automerge-repo/interfaces/_automerge_automerge-repo.DocumentProgress.html), [A3](https://raw.githubusercontent.com/automerge/automerge-repo/main/packages/automerge-repo/src/Repo.ts)); VS Code cancels superseded backup operations and shutdown work ([V2](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts)); Elm exposes `Process.kill` ([E5](https://raw.githubusercontent.com/elm/core/1.0.5/src/Process.elm)). | The interface must state whether cancellation withdraws one observer, supersedes one restore attempt, or tears down shared work. It must not silently convert an aborted wait into terminal restore failure. |
| Restart | Automerge's query can remain active after one wait is aborted ([A3](https://raw.githubusercontent.com/automerge/automerge-repo/main/packages/automerge-repo/src/Repo.ts)); VS Code retries backup restoration when a handler registers and tracks unrestored backups until handled ([V2](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts)); Elm makes restart a new message/effect sequence [Inference from the Model/Msg/Update loop] ([E1](https://guide.elm-lang.org/architecture/)). | Restart needs an attempt/epoch identity or an idempotent shared query so late results cannot activate a superseded Session. A persisted “loading” bit cannot prove readiness. |
| Terminal failure | Automerge exposes `failed` and `unavailable` query states and does not return a ready handle for them ([A2](https://automerge.org/automerge-repo/interfaces/_automerge_automerge-repo.DocumentProgress.html)); Elm `Task.attempt` delivers typed `Err` results ([E4](https://raw.githubusercontent.com/elm/core/1.0.5/src/Task.elm)); VS Code backup exceptions are caught and logged ([V2](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts)). | Terminal read-only recovery should be an explicit result/state, not an absent callback. The interface must distinguish “no authority yet” from “authority cannot be reconstructed.” |
| Authority readiness | Automerge returns a `DocHandle` only on `ready` and keeps `DocumentProgress` read-only ([A2](https://automerge.org/automerge-repo/interfaces/_automerge_automerge-repo.DocumentProgress.html)); a view-pinned handle rejects mutations ([A4](https://automerge.org/automerge-repo/classes/_automerge_automerge-repo.DocHandle.html)); UCAN requires execution-time authority validation ([U1](https://raw.githubusercontent.com/ucan-wg/spec/main/README.md)). | Readable canonical Markdown and editable causal authority should be separate values or separate states. A text snapshot must never itself authorize mutation. |
| Focus continuity | VS Code opens restored editors with `preserveFocus: true`, `inactive: true`, and `pinned: true` ([V4](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts)); Loomark's focus token carries target and source revision and post-render selection restoration checks the expected revision ([L5](../../apps/loomark/internal/rabbita/focus_runtime.mbt#L36-L74), [Loomark focus effect](../../apps/loomark/internal/rabbita/focus_runtime.mbt#L139-L217)). | Activation must be an ordered handoff that preserves scroll, focus, anchor, focus endpoint, direction, and UTF-16 bounds. A lifecycle callback alone is insufficient unless it carries the continuity snapshot or an equivalent correlation. |

## Deletion-test implications

**Method (inference):** Apply the codebase-design deletion test by asking whether deleting a module makes complexity disappear or forces that complexity to reappear across callers. The following are implications, not a selection of Loomark's interface:

1. **Automerge-shaped progress/capability module.** [Inference] If deleting the module forces Rabbita to reimplement readiness snapshots, subscriptions, shared-load cancellation, and mutation-capability gating, the module has earned depth. If callers only forward `peek()` and `whenReady()`, it is a shallow wrapper.
2. **VS Code-shaped lifecycle coordinator.** [Inference] If deleting the module spreads registration, supersession, backup cleanup, handler discovery, and focus-preserving activation across storage and UI adapters, the seam has high locality leverage. If it only relays events, delete it.
3. **Elm-shaped reducer.** [Inference] If deleting the reducer forces each callback to invent ordering, stale-result, restart, and terminal-failure rules, the reducer is deep. If it merely stores an enum while effects decide transitions, the enum belongs nearer the transition owner.
4. **Ports-and-adapters seam.** [Inference] If deleting the port leaks browser storage, archive representation, or causal-engine vocabulary into the Editing Document Session, it was protecting locality. If there is only one adapter and no variation or replacement test, the seam may be hypothetical; Cockburn's pattern is valuable when multiple adapters can satisfy the same purposeful conversation ([P1](https://alistair.cockburn.us/hexagonal-architecture)).
5. **Capability object.** [Inference] If deleting the capability lets any caller mutate a readable snapshot or bypass causal admission, the capability was carrying an authority invariant. If every caller still needs separate validity checks, it was not deep enough.

## Ranked lessons (not a design decision)

1. **Separate readable state from mutation authority.** Automerge's read-only `DocumentProgress` plus ready-only `DocHandle` is the clearest direct precedent; UCAN supplies the independent authority vocabulary. ([A2](https://automerge.org/automerge-repo/interfaces/_automerge_automerge-repo.DocumentProgress.html), [A4](https://automerge.org/automerge-repo/classes/_automerge_automerge-repo.DocHandle.html), [U1](https://raw.githubusercontent.com/ucan-wg/spec/main/README.md)) [Inference]
2. **Make terminal failure and unavailability first-class.** Automerge exposes both states, while Elm maps failed tasks into `Result` messages; neither requires a fake editable value. ([A2](https://automerge.org/automerge-repo/interfaces/_automerge_automerge-repo.DocumentProgress.html), [E4](https://raw.githubusercontent.com/elm/core/1.0.5/src/Task.elm)) [Inference]
3. **Specify cancellation scope and supersession.** Automerge distinguishes observer cancellation from shared-load teardown; VS Code cancels the superseded operation; Elm has explicit process killing. ([A3](https://raw.githubusercontent.com/automerge/automerge-repo/main/packages/automerge-repo/src/Repo.ts), [V2](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts), [E5](https://raw.githubusercontent.com/elm/core/1.0.5/src/Process.elm)) [Inference]
4. **Keep transition ownership in one deep module.** Elm concentrates state transitions in `update`; Cockburn requires a purposeful port conversation rather than technology leakage. ([E1](https://guide.elm-lang.org/architecture/), [P1](https://alistair.cockburn.us/hexagonal-architecture)) [Inference]
5. **Treat focus continuity as a correlated activation obligation.** VS Code makes focus preservation an explicit restore option, and Loomark already rejects stale focus revisions. ([V4](https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/common/workingCopyBackupTracker.ts), [L5](../../apps/loomark/internal/rabbita/focus_runtime.mbt#L123-L217)) [Inference]
6. **Do not promote a source pattern wholesale.** Automerge's shared query, VS Code's long-lived working copy, Elm's pure reducer, Cockburn's port, and UCAN's capability all solve different variation axes. Choosing a Loomark interface still requires a deletion test against the actual classification-to-Session seam. [Inference]
